# ADR-063 F1 comparator dispositions — independent source screen

Screen date: 2026-10-23; research baseline: 2026-10-22. This is a source capability screen, not reproduced model execution. No builds, installations, model loads, weight downloads, or performance tests were performed. Root owns the final F1 disposition and manifest.

Governing contract: hf2q `docs/adr/ADR-063-apple-silicon-four-agent-speed-coherence.md:57-83` requires screening BaseRT 0.4.0, MLX 0.32.4/current main and Kapitsa; identical hf2q-produced GGUFs define same-artifact lanes; native-format results require distinct quantization labels and independent quality evidence. None of these supplementary comparators replaces the mandatory current-peer arm.

Absence from PATH is not a capability verdict. A missing local executable should be recorded as `installation_not_inventory_verified` or `not_installed_at_observed_paths`, separate from format/family/protocol status. Do not label an engine globally unsupported because one target or one importer path is unsupported.

## BaseRT: exact integration required

Frozen screening snapshot: `basecompute/baseRT@24badc8dd173e4111b64996a718d0e056405ea62`, README SHA-256 `918f77c46cf9a4fc56dbac39154ad6473456ba5d6d513e5b7dbde4be410c0a59`. Snapshot README lines 18-30 describe the CLI/C API and `.base` format; lines 116-145 distinguish front-end commands from separately distributed runtime binaries and list local GGUF/HF/MLX-to-`.base` conversion. Thus “accepts GGUF as conversion input” does not establish execution of the identical GGUF representation. [Pinned README](https://github.com/basecompute/baseRT/blob/24badc8dd173e4111b64996a718d0e056405ea62/README.md).

Required next source/inventory probe: identify exact 0.4.0 tag/release-to-commit binding; inspect serving guide, CLI reference, supported architecture/quantization matrix and engine distribution/license. Inventory front-end and `basert-serve` runtime separately, recording actual `--version`/help behavior and binary hashes without loading weights. The README commit alone is not proof that the installed engine is 0.4.0. Inspect whether any direct-GGUF execution path exists before classifying that arm definitively.

The [pinned server API](https://github.com/basecompute/baseRT/blob/24badc8dd173e4111b64996a718d0e056405ea62/docs/reference/server-api.md) advertises `/v1/chat/completions`, streaming and tool calls; it does not prove exact Qwen3.8, DeepSeek4, Qwen3.6 or Gemma4 loaders or four simultaneously active conversations. After Q5 admission, probe four concurrent bounded tool-call/tool-result conversations, cache reuse/isolation, cancellation and valid SSE completion. For `.base` diagnostics, preserve HF source provenance, converter/config/output tensor inventory, quantization and calibration settings, hashes, exact templates/tokens and independent quality metrics. Do not substitute a catalog or prequantized download for the campaign artifact.

## Kapitsa: concrete Qwen applicability, conversion caveat

Frozen snapshot: `nace-ai/kapitsa@c490f8159622bb2d356b21c8d670d668997cbfb4`; README SHA-256 `a580dfb4a5f5033d150c75525df50aa91e540fc94b78b2ec9ce16e6c6f67be48`, KFlash docs SHA-256 `2238e038859c5745d116bfe46609b49a055e990a3812d9c1aadc074033b55a27`. [Pinned usage documentation](https://github.com/nace-ai/kapitsa/blob/c490f8159622bb2d356b21c8d670d668997cbfb4/docs/usage.md), archived usage snapshot, SHA-256 `54780e554b787ecb1af720b037d7b2040de267f49228c6d0438975ce88d19206`.

Usage lines 158-186 resolve a crucial ambiguity: `serve --model FILE.gguf` converts on first use; importer supports `qwen35`/`qwen35moe` and rejects other architectures. The conversion table changes several input precisions; some routed expert formats retain source blocks, which does not imply every tensor is unchanged. Therefore the advertised Qwen GGUF input path is useful but insufficient for strict same-artifact inclusion. Classify DeepSeek/Gemma **unsupported by this documented GGUF import path**, without claiming all future/native loaders impossible.

Next low-impact probe: inventory exact release/binary identity and `kapitsa import --help`/`serve --help`; inspect importer source and the campaign's actual GGUF architecture/tensor-type inventory. The documented `kapitsa import <exact-GGUF> --dry-run` is a metadata-only candidate, but verify implementation has no model load or implicit download before invoking. Record conversion output precisions and all discarded/added tensors, especially MTP. Do not run normal import/serve to discover applicability before admission.

Usage lines 249-256 expose explicit `--slots N`; require `--slots 4`, not automatic defaults that may choose two or three. Lines 307-315 discuss slot memory and tool-result follow-ups, while lines 371-375 advertise chat tools, streamed usage/cached tokens and reported slots. These are source-advertised behaviors only. After Q5, verify four occupied slots, isolation, retry/rewind, tool arguments and continuation under the actual frozen limits. KFlash docs lines 245-246 distinguish multi-slot eight-row behavior from a deeper one-slot draft lattice; freeze actual four-slot speculation policy, drafter hash and calibration/cache state. Headline single-slot gains are not four-agent evidence. Native-format Qwen diagnostics remain worthwhile even if the strict same-GGUF arm fails eligibility.

## MLX: identify the serving adapter, not just the array framework

The existing snapshot is `ml-explore/mlx@v0.32.4`, README SHA-256 `df7d58237b57e70595c5a19b72acb4053d28a47235033bd2cbfd66eea73e1c7d`. Its README describes an array framework; that is not a server identity. During this screen GitHub API resolved core main to `afc03c51105a8e25e70fa2ba0befb214e4f5ec6f` and official `ml-explore/mlx-lm` main to `59995f131cf2b48950a67d2eb36d76b2a554b989`; pin these separately rather than recording “MLX main.” These observations need timestamps and independent final manifest binding.

Use official [`mlx-lm.server` source at the observed commit](https://github.com/ml-explore/mlx-lm/blob/59995f131cf2b48950a67d2eb36d76b2a554b989/mlx_lm/server.py) for a concrete adapter screen. Archived server source snapshot, SHA-256 `8b6968a3aa1b3b4a70c70d85a9db94484c9722ea2e9ded7c7a4a69ca7930c6cd`: lines 907-911 configure BatchGenerator completion/prefill concurrency; line 1255 routes chat requests; line 1609 formats tools; lines 1912-1915 require MLX model weights/tokenizer/config. These establish inspectable implementation paths, not supported target families or direct GGUF execution.

Next probe: inspect exact adapter model registry, loader and tokenizer/tool parsers for all four target configurations, especially DeepSeek4 compressed/cache behavior; inspect loader format support rather than assume core GGUF reading implies server compatibility. Freeze adapter/package/dependencies, CLI concurrency flags, prompt cache configuration and speculation. Run metadata/help inventory only where importing the module is confirmed not to load weights. Test separate 0.32.4 and current-core environments only when dependency compatibility is documented; do not assume current mlx-lm is compatible with both. A compatibility failure is a version-pair disposition.

A native-format diagnostic must bind original HF revision, exact conversion/quantization process and output hashes, parser/template/token stream, then pass independent quality and four-conversation tool/SSE/prefix-reuse tests. Never present it as an identical-GGUF result. Third-party MLX servers such as oMLX or mlx-serve can be additional named adapters, but require their own source/binary/configuration screening; their capabilities cannot be inherited by MLX core or official mlx-lm.

## F1 manifest/status requirements and later probe contract

Record per engine AND per target: source revision, release mapping, runtime binary/package hashes, format route, architecture/quant-type applicability, slot/concurrency controls, native tool parser/template, prefix reuse, cancellation, speculation/drafter settings, memory admission status and proof receipt. Use separate statuses `source_advertised`, `source_inspected`, `metadata_probe_passed`, `runtime_reproduced`, `unsupported_documented_path`, `blocked_missing_evidence`. This screen supplies the first two selectively; it supplies no runtime passes.

Any later applicable arm must pass four actual independent occupied conversations with bounded tool execution rounds, a forced/verified tool argument payload, submitted tool result, semantic streamed continuation, prefix reuse, isolation and cancellation. Freeze exact limits and engine-best documented settings; do not disable speculation to handicap a comparator. Q5 admission, one-engine-at-a-time and cleanup prerequisites apply to supplemental arms too. Unsupported/native-format supplemental arms do not block defining a transparent F1 screen, but they do not fulfill the mandatory latest-peer runtime comparison or supply missing all-four speed evidence.
