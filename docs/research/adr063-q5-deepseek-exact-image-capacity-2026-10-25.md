# DeepSeek anchor-image exact requested capacity

Source implementation candidate based on `4fa53c24ee1b2e6eb279ffe858877b9d06c0552b`.
Independent source review and root-run checks accepted the bounded codec change,
as recorded below. The implementation author performed no build, test, device
or model execution. Hosted CI and integration remain pending.

The serializer now derives its image length from the actual cache plan,
seven buffer metadata roles and anchor position before reserving the image
or reading payload. A single fallible `try_reserve_exact(D)` is followed by
an explicit capacity-equality check. Every header, token, section and checksum
append checks its end against the planned length and reserved capacity before
mutation; the total-length patch is restricted to initialized bytes. Final
length and capacity checks execute at runtime. Small checked per-layer plan
metadata is separate from image payload. A new typed capacity error reports
reservation, layout and writer failures. No second image or shrink copy is used.

Valid codec bytes remain version 1: 40-byte header, LE u32 token ledger,
64-byte per-layer header, unchanged section order, patched total length and
32-byte SHA-256 trailer. Hydration, queue behavior, persistence frequency,
durability and async writer behavior are unchanged.

For the selected 43-layer context-262144 endpoint, cache payload
`A = 6880*C + 17842176 = 1821392896` bytes. This is the existing published
cache formula, not an image-size formula. The complete image includes tokens,
layer headers and framing: `D = A + 4*C + 64*L + 72 = 1822444296` bytes.
Other positions use the actual plan's window and compression-floor rules.
The earlier private CPU inventory that called A an image length understated D;
the published cache-payload claim remains intact.

Under the existing single producer plus one busy/one pending writer topology,
three distinct successful image vectors have requested capacity at most
`3*D = 5467332888` bytes at that endpoint. This is conditional image-vector
payload accounting, not a general bound for concurrent public serializer calls.
Allocator usable-size rounding, metadata, token/index/key clones, hydration,
dirty file pages/writeback and other I/O staging require separate bounds or
allowances. In particular, 3D does not include dirty file-cache payload.
No physical memory fit, Q5 admission, serving correctness or speed win is claimed.

Ten passing pure controls use the production metadata planner and emitter:
independently fixed old-format bytes and SHA; all seven roles and zero sections;
actual 43-layer plan arithmetic without image allocation; metadata/cardinality
and checked-overflow failures before reservation or payload callbacks; reservation
failure/anomalous capacity; wrong payload extents; append/patch/checksum quotas.
The tiny golden packet is explicit old-format bytes, not generated by the new
emitter. Root pure-validation command:

```sh
cargo test --locked --bin hf2q deepseek_image_ -- --test-threads=1
```

The separate ignored control below exercises the actual cache/hydration adapter.
Real-model serving stress remains separate. No new native dependency or API is used.


## CPU-accessible Metal codec control

At the historical V2 source handoff, root had compiled V1 and observed ten pure
tests pass; the added ignored control was not yet compiled or executed then.
Its later V3 execution is recorded below. It uses actual cache allocation,
snapshot, serialization, hydration and a second serialization, with tiny
three-layer ratios 0/4/128, context and position 128, head/index widths 32/16.
All physical source roots receive known CPU bytes before snapshot. Twelve
nonempty logical sections compare directly after hydration, including all
seven roles on ratio4; whole second image equality, checksum, ledger, position
and exact image capacity are required. Corrupt token bytes must fail at the
existing pre-allocation checksum guard. This source-order property is not a
runtime allocation-counter measurement; native0.15.3 exposes no such counter.
No encoder, command buffer, GPU submission or model is used.

Windows/compressed views alias attention parents and add no physical roots.

shape/plan metadata, allocator rounding, driver/device/runtime initialization
remain outside this payload subtotal, not claimed zero. All source and restored
owners remain alive through comparisons. No temporary full payload readback
Vec or extra snapshot is created. The control is below 16MiB requested payload.

The V3 control strengthening changed initialization: each physical root is initialized byte by
byte with `(index/251 + index%251 + layer*17 + role*29) % 256`, rather than a
constant root fill. The index-sensitive pattern distinguishes window and
compressed regions sharing one attention parent, so wrong view offsets cannot
hide behind identical region bytes. No array, root or image is added; the
requested packet and no-GPU contract remained unchanged. Compilation and actual
execution were pending at that historical source freeze; both passed below.
