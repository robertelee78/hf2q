## Decode hard-lock attempts (#233)

The owner observed `hf2q chat` freeze on its first prompt against a separate
`hf2q serve` in cmux: server busy/decoding, nothing reaching chat. Not
reproduced yet. Ruled out on this machine:

- chat-owned server and separate foreground server, first prompt and five
  fresh-session first prompts;
- 11-turn conversation, 6,000-token stream, 4 concurrent long streams;
- server terminal never read (pty blocked, 12 requests);
- 4 load-then-idle thermal cycles (fresh server, first prompt, 4 × 3,000-token streams for ~7.5 min, prompt right after, 4 min idle): no stall.

**Root cause found** after the owner shared a screenshot from another machine: the model was Qwen3.6-35B-A3B, not Qwen3.8. A templated prompt under 16 tokens ("hi" = 11) panics the engine thread on the qwen35/qwen35moe TQ cache layout (`gpu_full_attn.rs:6015`, `slot.k is None`); afterwards the server reports "warming up" forever and returns 503 to every request. Reproduced every time on 0.1.21; fixed on main by 27eb2995 (five short prompts clean). Details in #233/#234; the misleading "warming up" state is #250.

mlx-native waits on Metal command buffers with an unbounded
`waitUntilCompleted`, which matches "server busy, client sees nothing" if the
GPU never signals completion. `scripts/capture_hf2q_hang.sh` (PR #244) records
thread samples and GPU/thermal state when it happens again.

## Findings

1. **F1 — `hf2q chat` replies are capped at 512 tokens, reasoning included.**
   `hf2q chat` sends no `max_tokens`; the server default is 512
   (`src/serve/api/engine.rs` `SamplingParams::default`). Reasoning used up to
   391 of the 512, so long answers stop after about 120 visible tokens with
   `reason=length`. Every long-answer request in J2 hit it. Severity: high (user-visible truncation).
2. **F2 — some turns end with reasoning and no answer.** Turns 6 and 7
   produced 16 and 194 reasoning tokens then `stop` with no visible reply.
   Did not reproduce with the same prompt in a fresh conversation; context
   dependent. Severity: medium.
3. **F3 — the hf2q.us one-liner and `hf2q update` require Xcode developer
   tools.** Both called `/usr/bin/lipo`, an xcode-select shim that exits 69
   without accepted developer tools. Fixed in #242 (PR #243). Severity: high.
4. **F4 — uninstalling one installation deletes another's zsh completion.**
   Standalone install registers `/opt/homebrew/share/zsh/site-functions/_hf2q`
   (a machine-wide, user-writable path) as its own. A second installation
   (another account or isolated home) registers the same file, and its
   uninstall removes it while the first installation still owns it. The
   owner's file was restored from the identical per-user copy. Severity: medium.
5. **F5 — setup fails with an unclear error when `$HOME` contains a symlink.**
   `hf2q setup` in `HOME=/tmp/...` (`/tmp` → `/private/tmp`) fails with
   "setup filesystem: expected directory entry has the wrong type"; the same
   under `/private/tmp` works. The refusal may be intended; the message does
   not say which path. Severity: low.

6. **F6 — 0.1.21 `--glp` does not resolve Hub references.** The README
   documents `--glp owner/repo` and `--glp <huggingface.co file URL>`; 0.1.21
   treats both as local paths and fails with "GLP read error: No such file or
   directory". The current `main` resolves them (it correctly reports
   `ambiguous GLP files ... use a full Hub file URL` for a two-file repo), so
   the fix ships in v0.1.22. Severity: high for GLP users of 0.1.21.

7. **F7 — `--gcd` breaks tool calling and coherence.** With a tool offered
   (`tool_choice: auto` or `none`) the model never calls it, ignores the
   question, and the text degrades ("a simple lever system", doubled
   spaces). Severity: high for GCD users.
8. **F8 — `--gcd-schema` returns HTTP 500 when the schema object does not fit
   the token limit** ("grammar constraint was incomplete at length") instead
   of a length finish or a 4xx. Severity: medium.
9. **F9 — OpenCode fails on any tool schema with a bound over 2000.** HTTP 400
   `json-schema-to-grammar error ... maxLength: bound exceeds repetition limit
   2000` rejects every request when one MCP tool declares `maxLength: 4096`.
   Reproduced on main. Severity: blocker for agentic coding. Fix in #251.
10. **F10 — the 0.1.21 decode hard-lock** (see above): short prompts crash the
    qwen35/qwen35moe engine; fixed on main. The "warming up forever" symptom
    is #250.

Also measured during QE (#249): model download progress tracks completed Xet
chunks, not bytes received, so it looks hung and then jumps; the process held
~12 GB in memory during a 23 GB download.

## Impressions

Startup is fast (model load and warm-up 4 s). Chat is responsive at about
30 tok/s on this model. The 512-token cap is the most noticeable problem in
ordinary use: long answers just stop.
